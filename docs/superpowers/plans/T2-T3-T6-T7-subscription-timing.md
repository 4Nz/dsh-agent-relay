# T2、T3、T6、T7 订阅检查频率与总超时配置

## 用户要求与实现

2026-11-15 用户要求：默认 1 分钟检查频率、60 分钟订阅超时；上限为 1 小时检查频率、24 小时订阅超时；可在 DSH 会话中指定或在新建订阅页面设置。

检查频率使用 `check_interval_seconds`，范围 60～3600，默认 60。订阅总超时使用 `max_lifetime_seconds`，范围 60～86400，poll 默认 3600。页面单位为分钟，工具参数单位为秒。总超时从创建时间起算，活动和暂停不顺延；新 poll 的无活动截止与硬截止一致。push 默认寿命仍为 24 小时。

沿用 TypeScript、Node 定时器与 SQLite，不增加运行依赖或 schema 迁移。服务层、RPC、工具及前端共享同一配置。修改总超时时原子更新寿命与截止字段，从原创建时间计算；旧订阅不批量改写，旧超过一小时的周期在调度时限制为一小时。

## 实施与验证

- RPC 测试覆盖默认、最大值、超限无副作用及修改超时。
- 前端组件测试覆盖默认字段、上限、分钟转换及重新打开恢复默认。
- 工具测试覆盖会话参数转交服务。
- 计时器携带硬截止，检查频率长于剩余时间时在截止点触发，不循环空转。
- 暂停订阅在硬截止仍生成唯一 expired；查询跨截止且期间暂停时也先执行硬到期。截止后仍未完成的计时器标为 inactive，允许对账恢复。
- 完整交付检查、隔离 tarball 安装和日常 DSH 升级后页面核验。

## 使用示例

在 DSH 聊天中说「订阅这个 Codex 会话，每 5 分钟检查，2 小时后超时」，由模型调用 `relay_subscribe` 并传入 `check_interval_seconds:300`、`max_lifetime_seconds:7200`。创建成功后的订阅记录才是配置生效证据；模型仅复述意图不等于已经创建。

旧接口 `idle_timeout_seconds` 保留兼容，新请求优先使用 `max_lifetime_seconds`。本机不能替代 macOS 的真实宿主验收。
