# T5.3 WorkBuddy Adapter 接入实现计划

2026-11-18 范围补充：本文保留默认只读接入设计。独立实验发送现已按 [T5.3 ACP 实验计划](T5.3-workbuddy-acp-experiment.md) 实施，但生产注册不启用；真实投递仍未确认，详见 [验证记录](../../research/T5.3-workbuddy-acp-validation.md)。下文“始终只读”等表述仅指默认接入，不包含显式实验配置。

> 状态：只读 Adapter 与本地验证已实施；真实 live 会话、通知 Skill 回传和已有 SQLite 数据库结构迁移仍未完成。本文记录实现方案与验收边界，不代表真实消息投递已经打通。

**目标：** 为 DSH Agent Relay 增加只读 WorkBuddy Adapter，使 Relay 能发现 WorkBuddy 会话、读取实时或离线进展并执行订阅检查；WorkBuddy 向 DSH 的主动结果通知由 WorkBuddy 侧安装的通知 Skill 完成。

**架构：** Adapter 由网关客户端、token/进程判活和历史读取回退三个边界组成，只实现会话发现、快照和增量读取，不实现 WorkBuddy 入站发送。网关优先提供实时状态与会话内容；网关对历史会话返回 `404 SESSION_NOT_FOUND` 时，使用只读本地 JSONL 作为正文回退。WorkBuddy 侧的 `dsh-notify` Skill 通过已有通知入口把完成摘要推回 DSH，订阅、检查、通知和 DSH 判断继续复用现有服务层。

**技术栈：** Node.js >=24、TypeScript ESM、Node 内置 `fetch`、`node:fs/promises`、`node:path`、`node:crypto`；不新增运行时依赖，不直接修改 WorkBuddy 数据库或会话文件。

**规格依据：** `docs/roadmap/tasks.md` 的 T2.1、T2.2、T4、T5；`docs/superpowers/plans/T5.3-skill-agent-integration-assessment.md`；WorkBuddy 本机验证材料位于用户工作目录，不作为仓库运行时依赖。

## 全局约束

- WorkBuddy 只作为后续 Agent 接入，不改变第一版 Claude/Codex 的既有行为。
- 所有路由使用准确的 `(agent, external_session_id)`，标题和工作目录只用于展示与人工核对。
- WorkBuddy 网关密码只从 `~/.workbuddy/.gw-token` 读取；不读取、记录或输出密码，不尝试从外部进程环境猜测 `CODEBUDDY_GATEWAY_PASSWORD`。
- 不把完整会话正文、token、无关会话内容写入日志、测试输出或仓库。
- 查询失败只能返回检查失败或 `unknown`，不能推断任务已完成。
- WorkBuddy Adapter 的 `sendMessage=false`、`runPrompt=false`；不能通过 Relay 反向注入提示词或要求 WorkBuddy 安装 Skill。
- 真实冒烟使用专用 WorkBuddy 会话，与业务会话分离；当前实测没有 live 会话，实时发送不属于本方案验收范围。

## 二、接口与状态设计

### 2.1 WorkBuddy Adapter 对现有接口的映射

新增 `agent: "workbuddy"` 的 Adapter，继续实现现有 `AgentAdapter`：

| Relay 能力 | WorkBuddy 实现 | 失败映射 |
| --- | --- | --- |
| `listSessions()` | 网关 `GET /api/v1/sessions?cwd=*`；必要时合并 `/sessions/across-projects` 去重 | 网关不可用返回 `AdapterError("unavailable")` |
| `snapshot(sessionId)` | 先查会话元数据；再按网关 `history/replay`、本地 JSONL 顺序读取 | 404 触发回退；文件不存在或解析失败返回检查失败 |
| `incremental(sessionId, baseline)` | 网关 replay 或 JSONL 增量解析，按游标返回新事件 | 游标不兼容返回 `parse_error`，不得返回空增量冒充无变化 |
| `sendMessage(sessionId, text)` | 不实现，始终通过能力声明拒绝 WorkBuddy 入站发送 | 返回 `rejected`，原因固定为“WorkBuddy Adapter 只读” |
| `runPrompt(text)` | 不实现；Relay 不通过 WorkBuddy Adapter 运行安装或执行提示词 | 返回 `rejected`，原因固定为“WorkBuddy Adapter 不支持执行提示词” |
| `capabilities()` | `listSessions=true`、`snapshot=true`、`sendMessage=false`、`runPrompt=false`；网关不可用时保留只读能力但在结果中报告检查错误 | 页面和工具显示实时不可用原因 |

`external_session_id` 只使用 WorkBuddy API 返回的会话 ID。不得按标题、cwd 或列表顺序推导目标 ID。

### 2.2 活跃与忙碌的定义

三个状态分别计算：

1. **进程存活：** `~/.workbuddy/sessions/*.json` 中存在 `kind == "interactive"`，`lastHeartbeat` 距当前小于 60 秒，且 PID 与 token 元数据一致；再用 `/api/v1/health` 返回 200 确认端口和凭证有效。
2. **当前 live：** `/api/v1/sessions/live.data.sessionId` 等于目标会话 ID。`sessionId == null` 表示没有当前交互会话，但不影响对历史 JSONL 的只读读取。
3. **正在执行：** `/api/v1/status.data.busy == true`，或 `runStatus`/replay 中存在未终结的工具调用。`writerOccupied` 作为网关写入通道占用信号单独保留。

订阅检查使用 live/busy 只判断事实来源的新鲜度：live 会话可提供网关实时状态，非 live 会话只能使用历史快照或 JSONL，不能把历史 `pending/working` 当作当前空闲。`busy`、`writerOccupied` 和 heartbeat 必须进入 `Snapshot.runtime_note` 与 `status_context`，供 DSH 判断是否需要继续检查；它们不产生 WorkBuddy 入站发送能力。

### 2.3 token 刷新与失效恢复

- `TokenProvider` 每次操作重新读取 `~/.workbuddy/.gw-token`，校验 JSON、端口范围、PID、`0600` 权限和 `savedAt` 存在；不缓存密码。
- 读到 401、连接失败或 PID/heartbeat 不匹配时，Adapter 写入 `~/.workbuddy/.gw-refresh-request`，只记录失败原因、时间和来源，不写入凭证。
- 外部 DSH 进程不执行 refresh。WorkBuddy 会话内 Skill 或 `SessionStart` hook 负责读取该标记并运行 `wb-gw-token.py refresh`；下一次 Adapter 调用重新读取 token。
- token 刷新本身成功与否必须由下一次 `/health` 200 确认；401 不能被转换为“会话关闭”。

### 2.4 历史读取回退

按以下顺序读取：

1. 用 live 或当前网关调用 `GET /api/v1/sessions/{id}/history`，获取逐轮摘要。
2. 需要工具事件或 history 返回 404 时调用 `GET /api/v1/sessions/{id}/replay`。
3. `history/replay` 返回 `404 SESSION_NOT_FOUND` 时，根据会话元数据的 `projectId`/cwd 安全解析 `~/.workbuddy/projects/<project-key>/<session-id>.jsonl`，以只读方式逐行解析。
4. JSONL 解析 `message`、`reasoning`、`function_call`、`function_call_result`；只向 Relay 返回用户消息、模型回复、工具调用摘要和游标，不把原始行写日志。
5. 找不到文件、文件正在写入或 JSON 损坏时返回 `AdapterError`，并在 `Snapshot.runtime_error` 中说明读取失败；不得将失败转换为 `closed=true`。

网关和 JSONL 两种来源都要带 `status_context`，说明 `runtime_source`、`turn_status_source` 和历史状态范围，避免把历史 `pending/working` 当成当前实时空闲或完成。

游标采用 `{uuid, timestamp, target_turn_id, turn_status}`：网关来源以事件 ID/时间戳为基线，JSONL 来源以文件 inode 与行偏移派生稳定 UUID；文件被替换时重新建立基线并返回 `has_more`，不重复发送旧事件。

### 2.5 入站发送边界与通知 Skill

WorkBuddy Adapter 不实现 `sendMessage`，也不通过 `/reply`、`/runs` 或任何本地数据库写入向 WorkBuddy 注入消息。这样可以避免历史会话 404、live 为空、目标回退和权限提升造成误投。

WorkBuddy 的主动通知走另一条方向：安装阶段向 WorkBuddy 提供 `dsh-notify` Skill，让 WorkBuddy 在任务完成、失败或超时时调用本机 DSH 通知入口。通知正文只发送结果摘要、真实 WorkBuddy 会话 ID 和稳定 `request_id`，不上传完整历史。Relay 侧按现有 T2.6/T3.3 处理凭证、幂等、接收会话和投递状态。

由于 WorkBuddy Adapter 的 `runPrompt=false`，Relay 不能通过现有 `skill-install.ts` 的“调用外部 Agent 执行安装提示词”路径完成安装。安装必须采用以下受控路径之一，并在产品中明确展示：

1. WorkBuddy 用户在 WorkBuddy 会话内执行安装指引，由 WorkBuddy 自己写入 Skill；或
2. 后续新增独立的 WorkBuddy Skill 文件安装器，只复制受信任的 Skill 包到固定目录，并在写入前展示路径、备份原文件和自检结果。

本方案采用路径 1 作为第一阶段，路径 2 单独立项；不得把任意 shell 命令或 Markdown Skill 内容拼接进 Relay 的 Adapter 调用。

## 五、补测前提与明确限制

WB-11/WB-12 之前必须在 WorkBuddy 中打开专用会话，并由 WorkBuddy 自己安装 `dsh-notify` Skill；如果 App 重启，还要在 WorkBuddy 会话内运行 `wb-gw-token.py refresh`。通知测试只发送结果摘要、真实会话 ID 和稳定 request_id，不上传完整历史。没有 live 会话时，Relay 仍可以读取历史 JSONL，但不能声称具有 WorkBuddy 入站发送能力。

本方案允许网关读取失败时回退到本地 JSONL，但 JSONL 只证明历史事实，不能提供当前实时 busy、writer 持有或可发送能力。历史 JSONL 的读取结果必须标记为历史来源；DSH 不能根据它单独判定任务已完成或当前空闲。

计划完成后，实施者应将本文件与 `docs/research/T5.3-workbuddy-adapter-validation.md` 的真实结果一起评审，再决定是否把 WorkBuddy 的只读订阅和通知 Skill 从“后续 Agent”纳入正式路线图。
