# T1 存储实现计划

> **供 Agent 执行者：** 必须使用 `superpowers:subagent-driven-development` 或 `superpowers:executing-plans`，逐任务执行本计划。使用复选框跟踪进度。

**目标：** 为 T2 提供可重启恢复、带约束与原子操作的 SQLite 存储模块，保存订阅、一次性通知与外发消息。

**架构：** 使用 T0 已选定的 `node:sqlite`，提供独立于 Cordis、Adapter 和 HTTP 的存储模块。以 SQL 约束保证记录合法性，以同步事务保证通知与订阅的状态一致；DSH 负责提供数据目录和调用生命周期。

**技术栈：** 建议采用 JavaScript ESM、Node.js >=24.0.0、`node:sqlite` 的 `DatabaseSync`、`node:test`。本机已确认 Node.js v24.14.0；这是本计划提出的运行基线，不继承 T0 包示例中的 Node >=20。无第三方运行依赖，无编译步骤。

**规格：** `docs/tasks.md` 的 T1；`docs/T1-storage-design.md`；`docs/dsh-plugin-development.md` 的 T0.2、T0.3。下述“待确认决策”经评审后应同步回规格，避免执行者在矛盾文档间自行选择。

## 全局约束

- “DSH 和外部 Agent 在同一台机器上。”
- “第一版按本机单用户设计，表里保留所有者字段。”
- “同一订阅只会产生一条通知，由唯一约束保证。”
- “历史数据默认保留 30 天，由定时任务清理。”
- “不直接修改外部 Agent 的历史数据库或会话记录，不绕过其权限策略。”
- 保留 `relay_message` 名称；文档使用中文、任务文档文件名与一级标题含 T1、提交信息使用中文。
- T1 不实现外部执行、定时任务、工具、HTTP 或页面；清理仅提供函数，日调度属于 T2.8。
- 所有命令使用 `rtk`；在当前独立 worktree 执行，主目录保持 `main`。

## 评审重点

1. 两个数据库连接同时登记同一通知：仅一个成功，终态与通知保持一致（任务 3）。
2. 通知清理后的迟到请求：已结束订阅仍拒绝新通知（任务 4）。
3. 发送或投递中途退出：保留未知状态，不能自动重发（任务 4）。
4. 同一时间戳的分页记录：以 ID 决胜，无重复遗漏（任务 2）。
5. 已有数据库版本更高或迁移失败：拒绝打开或回滚，不能静默覆盖数据（任务 1）。

## 待确认决策

这些是本计划建议，尚不表示用户已确认；执行任务 1 前一并评审：

- 采用上述 JavaScript ESM 技术栈；未来插件入口可直接导入，不在 T1 引入 TypeScript 构建链。
- 用户已确认：push 在通知送达 DSH 会话、触发该会话开始处理后结束为 delivered，不等待 DSH 回复完成。现有 followup 返回不等于已验证的持久接收与唤醒确认，具体确认依据必须在 T2 接入时验证。poll 生成通知与结束订阅同事务。修订 T2.5 的概括性表述。
- poll 的 `dsh_session_id` 必填，周期最小 60 秒；push 可空。周期不设置隐含默认值，由调用者明确传入。
- 用户已确认：使用插件级共享 token，本机所有外部 Agent 共用，在 DSH 设置页面统一配置和重置。订阅不保存 token；插件配置仅保存 token 摘要，明文生成后一次展示，重置后旧 token 失效。通知请求以共享 token 认证，以 subscription_id 路由；页面和认证实现归 T6 / T2.6。
- 用户已确认：投递最多尝试 3 次（包括首次，即最多重试 2 次）。保存 delivery_attempts、max_delivery_attempts=3、next_attempt_at、delivery_key；服务层安排退避，存储层阻止第 4 次 claim。每次尝试使用相同 delivery_key；未知结果先核对，不能盲目重试。接收端幂等尚待真实验证，不能只凭本地唯一键宣称完成。
- 用户已确认：通知和消息不论状态，按 created_at 满 30 天统一删除，不设置未知或进行中例外；订阅保留作为防重依据。
- 数据路径由调用者传入绝对数据目录，固定文件名 `agent-relay.sqlite`，不猜测 DSH 数据根目录，也不把数据库存入仓库。

| 文件 | 职责 |
| --- | --- |

| `src/storage/schema.js` | v1 表、索引、约束与迁移列表 |
| `src/storage/records.js` | 输入校验、snake_case 记录与 JSON cursor 编解码 |
| `src/storage/subscriptions.js` | 订阅增查、条件更新与分页 |
| `src/storage/notifications.js` | 原子登记通知、投递状态与订阅联动 |

记录字段沿用 T1 草案的 snake_case。ID、owner 与路由字段为非空字符串；ID 由调用者提供。时间存 UTC Unix 毫秒非负安全整数，接口时间转换留给 T4。cursor 为可序列化 JSON 值或 null，禁止 undefined、循环引用和非 JSON 数值。可空字段返回 null。列表返回 `{ items, next_cursor }`，默认 limit=50，允许 1..100；游标结构为 `{ created_at, id }`，排序 `created_at DESC, id DESC`。

订阅增加 `notification_recorded_at`（可空时间），首次登记通知时在同一事务中写入，之后不可清空；即使 active push 的通知被清理，该字段仍阻止重复创建。通知增加 `delivery_attempts`（初始 0）、`max_delivery_attempts`（固定 3）、`next_attempt_at`（可空毫秒）、`delivery_key`（非空且唯一，等于通知 ID）。消息状态与任务原文一致。所有更新要求 expected_status，不提供任意字段更新或原始 SQL 公共接口。找不到返回 null；校验失败抛 TypeError；条件更新失败返回 false；SQLite 忙锁错误向调用者传播，不能报告成功。

### 任务 3：通知防重与原子终态

**文件：** 新建 `src/storage/notifications.js`、`test/storage/notifications.test.js`。

**消费：** 任务 1 的 transaction，任务 2 的记录校验。**产出：** `createNotifications(db)` 返回 `getBySubscription(id)`、`record({notification,now}) -> { outcome, notification }`、`claim({id,now}) -> boolean`、`finish({id,status,now,error,next_attempt_at}) -> boolean`、`listDue({now,limit}) -> Notification[]`。outcome 为 created / duplicate / inactive；inactive 时 notification 为 null。

- [ ] **步骤 1：写失败测试。** active poll 登记 completed 后通知 pending、订阅 ended/completed；在写入通知后故意制造更新错误，两表均回滚。push 登记后仍 active，claim 后 finish delivered 才结束为 delivered。duplicate 返回原记录、不覆盖 summary。paused/ended 不接受新记录，source 与类型不符拒绝。
- [ ] **步骤 2：验证失败。** `rtk proxy node --test test/storage/notifications.test.js`，预期缺失模块失败。
- [ ] **步骤 3：实现接口。** BEGIN IMMEDIATE 后读取已有通知，有则返回 duplicate；再检查订阅 active 且 notification_recorded_at 为空，插入通知并设置该时间；标记存在但通知已清理时返回 inactive。claim 仅允许 pending 或到期 failed→delivering，且 delivery_attempts < max_delivery_attempts=3，原子增加 delivery_attempts 并清空 next_attempt_at。finish 只接受 delivering→delivered/failed/unknown；failed 可有下一次时间，unknown 不可有；listDue 只选 pending 和到期 failed。push 送达时若已被用户停止则保持 user_stopped，不覆盖终态；投递成功本身仍如实记录。
- [ ] **步骤 4：验证通过。** 运行步骤 2 命令。使用两个 worker_threads、各自连接同一临时文件并发 record，断言恰好一个 created、一个 duplicate、通知数量为 1；随后重开连接核对终态。覆盖 claim 竞争仅一方成功、unknown 永不进入 listDue、第 3 次失败后不再进入 listDue且第 4 次 claim 返回 false、三次尝试的 delivery_key 不变、sent/delivered 不等于外部任务完成。
