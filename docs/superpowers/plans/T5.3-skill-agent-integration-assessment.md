## 初步评估结论

Skill 可以兼容 Agent Relay，但适合放在“意图编排、参数收集和用户确认”这一层，不能替代当前 Adapter 的核心职责。建议采用“两层接入”：

1. 继续保留内置 Adapter，负责会话发现、快照、运行状态判断、消息发送和结果归一化。
2. 增加可选的 Skill Bridge，让某些 Agent 或特殊场景通过已安装 Skill 暴露的命令/API 接入；Bridge 的输出必须转换成现有 `AgentAdapter` 的统一结果，再交给订阅、检查和转发服务。

这样可以覆盖特殊 Agent、企业内部 Agent 和只提供命令行/HTTP Skill 的场景，同时不让模型文本直接改变订阅状态、绕过幂等或伪造“已发送”。

## 当前实现提供的基础

当前注册表按 `agent` 查找 Adapter，服务层只依赖以下统一能力：

- `listSessions()`：列出候选会话；
- `snapshot(sessionId, baseline)`：返回游标、运行状态、是否关闭、已结束轮次和最后回复；
- `sendMessage(sessionId, text)`：返回 `sent`、`rejected`、`failed` 或 `unknown`；
- `capabilities()`：声明支持的操作。

DSH 的 Skill 是 `.agents/skills` 目录中的 Markdown，由 Skill 文件系统发现。它本身是给模型看的使用说明，不是一个带事务和类型约束的插件接口。当前工具已经是服务层的稳定入口，Skill 只需要指导模型何时调用工具、如何让用户确认目标、如何解释状态。

因此，当前架构已经具备 Skill 兼容的“上层入口”，但还没有 Skill 作为外部 Agent 接入协议的运行时桥接。

## 能力适配判断

| 场景 | 是否适合用 Skill | 建议 |
| --- | --- | --- |
| DSH 模型判断用户是在订阅、查阅还是发送 | 适合 | 用 DSH 侧 Skill 指导调用 `relay_*` 工具 |
| 多个候选会话时让用户确认 | 适合 | Skill 展示标题、cwd、最近活动和 ID；最终仍传确定的 ID |
| 发送前复述目标、区分“已发送”和“已完成” | 适合 | Skill 负责话术和流程，状态以工具返回值为准 |
| 外部 Agent 完成后主动通知 DSH | 适合，但依赖入口 | Skill 调用本机 CLI/HTTP 客户端；服务端仍需 T2.6 push 入口和认证 |
| 列出外部会话、读取增量、判断 busy/held | 不宜仅靠 Skill | 需要 Adapter 或 Skill Bridge 返回结构化数据；不能解析自然语言作为状态 |
| 向外部会话发送消息 | 不宜仅靠 Skill | 需要受控 Adapter/Bridge，执行前检查占用状态并记录消息状态 |
| 订阅创建、结束、通知防重、重启对账 | 不适合 | 必须由现有服务层和 SQLite 事务保证 |
| Agent 自定义的一次性操作 | 可选 | 作为独立 Skill 工具执行，但不纳入 Relay 核心完成判定，除非提供统一协议 |

## 推荐的 Skill 形态

### DSH 侧 Skill

新增一个随插件安装的 Skill 文件，内容只描述流程和工具用法：

1. 先调用 `relay_list_sessions`，候选多于一个时向用户确认；
2. 创建订阅前复述 Agent、外部会话 ID、标题和接收 DSH 会话；
3. 发送消息前确认目标，向用户明确“已发送”只代表外部 Agent 已接收；
4. 看到定时提醒后调用 `relay_check`，不要凭提醒文本自行判断完成；
5. 对 `rejected`、`failed`、`unknown` 分别说明原因和下一步。

Skill 不应携带会话正文、凭证或自行拼接 SQL/HTTP 请求。工具返回的能力列表应优先于 Skill 中的静态示例，避免 Codex 等只读 Agent 被误导为可发送。

### 外部 Agent 侧通知 Skill

外部 Agent 的 Skill 只负责把“用户要求完成后通知 DSH”转成受控请求：

1. 先通过 DSH 提供的注册接口创建 `push` 订阅，取得订阅 ID；
2. 将订阅 ID、Agent 名称和外部会话 ID 写入当前任务上下文；
3. 任务结束时发送结果类型和摘要；
4. 只把服务端确认的响应当作“通知已登记/已接收”。

Skill 不应保存共享 token 的明文，也不应自行判定重复通知成功。凭证由本机配置提供给 CLI/HTTP 客户端，服务端按订阅唯一约束防重。当前 push HTTP、共享凭证和 push 时新建接收会话尚未实现，不能在现阶段把该 Skill 宣称为可用能力。

## Skill Bridge 设计建议

对需要 Skill 接入的特殊 Agent，增加一个可选 Bridge，而不是把 Markdown 直接注册为 Adapter：

```ts
interface SkillBridge {
  readonly agent: string;
  describe(): {
    listSessions: boolean;
    snapshot: boolean;
    sendMessage: boolean;
    push: boolean;
  };
  invoke(operation: "listSessions" | "snapshot" | "sendMessage", input: unknown):
    Promise<unknown>;
}
```

Bridge 的实现可以调用本机命令、Unix socket 或 loopback HTTP，但必须满足以下约束：

- 输入使用显式 JSON 参数，不把用户文本拼进 shell 命令；
- 输出使用版本化 JSON 信封，例如 `{version: 1, ok: true, data: ...}`；
- 在 Bridge 边界完成 schema 校验、超时、退出码和敏感字段过滤；
- 将错误映射为 `AdapterError` 或现有 `SendResult`，不得把原始会话正文写入日志；
- 每个 Agent 仍在注册表中对应一个唯一 Adapter 名称；
- Bridge 不直接访问 SQLite，不直接改订阅或通知状态；
- 发送操作必须返回明确的 `sent/rejected/failed/unknown`，超时只能是 `unknown`；
- 对不支持的能力返回 `false`，不能通过 Skill 文档暗示支持。

最小落地方式是实现一个通用 `command-json` Bridge：配置命令路径和允许的操作，按 stdin/stdout 交换 JSON。后续如果某个 Agent 有稳定的本机协议，再实现专用 Bridge。不要让 Bridge 直接执行任意 Skill Markdown 中的代码或任意 shell 片段。

## 为什么不能让 Skill 直接替代 Adapter

Skill 有三个结构性限制：

1. **可靠性不足**：Skill 由模型理解并执行；模型可能漏调工具、重复调用或误读“任务完成”。订阅防重和状态转换必须由服务端原子完成。
2. **状态不完整**：Skill 通常只能获得 Agent 自己愿意暴露的描述，无法稳定提供游标、基线之后的增量、进程持有状态和归档状态。
3. **安全边界不清**：把 token、会话 ID 或命令拼接交给模型，容易产生越权路由、重复通知和凭证泄漏。

因此，Skill 可以是“控制面”和“用户体验层”，Bridge/Adapter 才是“数据面”和“事实来源”。

4. **T5.4（可选）**：为有稳定协议的特殊 Agent 增加专用 Bridge，并补真实会话冒烟测试。

## 验收建议

Skill 兼容性验收应覆盖“模型流程”和“服务端事实”两部分：

- DSH 侧 Skill 在多候选时先确认，目标 ID 传递正确，Codex 发送能力正确置灰或拒绝；
- 外部通知 Skill 能登记一次 push、发送一次结果摘要，重复请求得到幂等响应；
- Bridge 的 malformed JSON、超时、非零退出码、未知字段和超长输出均有确定错误映射；
- Bridge 返回 `sent` 后才创建发送后订阅；`unknown` 不自动重发；
- 重启后订阅、通知防重和 Bridge 调用不会生成重复记录；
- 真实冒烟测试使用专用 Agent 会话，记录 Agent 版本、Skill/Bridge 版本和未验证项。

## 范围结论

“兼容 Skill”可行，但应定义为兼容 Skill 驱动的接入流程，以及可选的结构化 Skill Bridge。Skill 本身不能成为 Adapter 的替代品，也不能成为订阅状态的事实来源。第一版继续以内置 Claude/Codex Adapter 为默认路径；特殊 Agent 只有在提供稳定、可校验、可超时控制的 Bridge 协议后，才纳入 Relay 的统一能力。
