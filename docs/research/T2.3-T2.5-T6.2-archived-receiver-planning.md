# T2.3 / T2.5 / T6.2 归档接收会话导致新建订阅未规划频率

记录日期：2026-11-18；时间为 Asia/Shanghai。

## 现象与根因

从页面「新建订阅」创建关注后，看板持续显示「待 DSH 规划」「尚未选择频率」与「已送达 · 1 条待处理事件」，最近检查为空。

只读核查指定记录：关注处于 active / pending，selected_interval_seconds 和 schedule_task_id 均为空。16:39 的 planning 事件已入接收会话 inbox，Relay 批次标记 delivered；宿主随即启动一轮，但约 160 毫秒后以 blocked 结束，没有进入模型 step，也没有调用 relay_plan。

实际接收会话是旧路由复用的 DSH 会话，其 ID 仍在宿主 workspaceRegistry.archivedSessionIds 中。宿主 ArchivedSessionGate 明确拒绝归档会话进入模型步骤。插件原有 listSessions 存在性校验没有排除归档，因此误把保留历史的归档会话当作可接收目标；idle 也不能代表会话获准执行。

这是接收端生命周期校验遗漏，不是频率显示丢失，也不是 Codex 被持有导致禁止投递。页面按现有设计交给 DSH 规划频率，未规划时不应伪造每 60 秒检查。

## 修复范围

- 新建订阅候选排除归档的 DSH 会话。
- 显式选择、工具当前会话和旧路由自动复用均通过同一接收资格校验；已归档时在创建关注或发起外部发送之前明确拒绝，提示恢复原会话或选择未归档会话。
- 投递层不向归档会话发起 followup；等待加载实例后再次核对归档状态。桥梁空闲检测同样排除归档，保留待投递事件。
- 归档状态每次从宿主读取，不缓存。不会自动解除归档、改绑路由、清空历史批次或填入默认频率。

## 已有记录的处理

本次代码修复不会追溯重写已经 delivered 的批次。对已被宿主 blocked 的规划请求，先在 DSH 恢复原接收会话，再由 DSH 使用 relay_batch 读取原批次、relay_plan 选择频率、relay_decide 确认；也可结束原关注后重新创建，并明确选择一个未归档的接收会话。解除归档本身不保证被丢弃的那条输入自动重放。

本轮只读核查真实记录，未解除归档或改动生产订阅、队列、宿主历史。恢复未完成前，不能把截图中的订阅描述为已经开始定时检查。

## 验证

- 回归测试先在旧实现下失败，修复后通过：归档候选过滤、动态解除归档、默认复用归档路由拒绝且不落库、明确选择其他接收会话后生成规划事件、归档会话 idle 仍不投递、加载实例期间归档也不入队。
- `rtk npm run release:prepare` 通过：类型检查、305 项测试、干净构建、包清单检查及隔离 tarball 安装冒烟通过；`git diff --check` 通过。单测与安装包检查不替代真实 DSH 恢复后的验收。
