关注已改为固定24小时单主题持续关注，用户频率优先，否则DSH选择；增量由模型判断并确认，单轮完成不自动结束，结束后push不自动重订阅。以下为2026-11-11历史探测与候选方案，不代表当前全部实现/验收状态；历史专项记录见 [T2.7 / T5.2 / T6 / T7](T2.7-T5.2-T6-T7-codex-daemon-send-validation.md)，本轮完整真实T7仍未完成。

验证日期：2026-11-11（Asia/Shanghai）。依据：本仓库 README、本机 CLI/daemon、Codex 桌面工具及官方 App Server 文档。本文是方案与验证报告，尚未实现 DSH 插件。

## 1. 结论

**指定会话的历史查阅已实测可行；向任意桌面端现有会话可靠转发消息，目前只能判定为有条件可行，不能宣称端到端验证通过。**

Codex 提供读取历史、恢复会话、开始新一轮和向执行中轮次补充消息的协议。但前提是接入正确的执行实例。相同 CODEX_HOME 和 threadId 不代表相同运行时。

本机存在两个不同的 app-server：一个后台 daemon 使用 Unix socket；另一个由桌面应用启动，通过 stdio 通信。daemon 能读到桌面端会话的持久化记录，却未持有其当前执行状态。因此不能用“daemon 返回 notLoaded”判定会话空闲，也不能直接恢复同一会话并启动并行执行。

建议第一阶段交付“可靠查阅 + 能力明确的转发”：查阅可使用历史协议；转发仅对已确认执行实例归属的会话开放。若第一阶段必须支持所有现有桌面会话，需要先补齐桌面桥接能力并完成真实投递测试。

## 2. 接入路线比较

| 路线 | 优点 | 限制 | 建议 |
| --- | --- | --- | --- |
| 连接持有目标会话的 app-server | 结构化状态、事件、消息转发；可保留上下文 | 必须找到原实例及可接入端点；本机桌面实例目前使用 stdio | 作为正式 adapter 的首选，逐实例验证 |
| 经 Codex 桌面工具桥接 | 已提供 list_threads、read_thread、send_message_to_thread 等能力 | 当前工具属于 Codex 内部环境，尚未证实 DSH 能直接调用或存在通用外部入口 | 桌面会话的候选桥接方案，不能当作已接通的 API |
| 独立 app-server / CLI resume | 易运行，可读取持久化历史，支持恢复上下文 | 无法天然掌握另一个进程的实时状态；并发恢复会产生执行冲突风险 | 可用于历史查阅；仅在确认原执行实例已释放会话后承接执行 |
| 直接读 SQLite / rollout、模拟界面输入 | 可作为诊断手段 | 存储格式与 UI 易变化；不能证明实时状态和投递成功 | 不作为正式转发通道，不直接修改 Codex 数据库 |

这里的选择是技术建议，并非用户已批准的实现决定。

## 3. 组成与绑定

```text
DSH 对话 / DSH 定时任务
          ↓
Relay 服务：订阅、鉴权、目标解析、消息 outbox、记录
          ↓
Codex Adapter（运行在 Codex 所在主机）
          ↓
明确标识的 Codex 执行实例 → threadId → turnId
```

DSH 和 Codex 不在同一主机时，在 Codex 主机运行轻量桥接服务；DSH 通过受认证的隧道或 HTTPS 访问。无需为了插件重新启动或管理用户的 Agent 环境；执行实例不在线时报告不可达。离开电脑后机器仍需开机、联网且未休眠，否则只能返回带时间戳的缓存和离线状态。

一条绑定至少保存：

- `agent=codex`、`hostId`、`instanceId`、`threadId`、目标 DSH 会话 ID。
- 会话标题、工作目录，用于展示和人工核对；路由只使用明确 ID，不按标题模糊发送。
- 连接方式和能力：历史读取、实时状态、新轮次消息、执行中补充、审批回复。
- 最近成功检查时间、最近观察到的 turnId、轮次状态、内容摘要 hash。
- 实例归属可信度；无法确认归属时不开放写入。

`instanceId` 是 Relay 自己定义的实例标识，不假设 Codex 有同名协议字段。不能把多个可读同一份历史的进程当作同一实例。

## 4. 会话查阅流程

1. 通过 `thread/list` 列出候选，用户指定会话 ID 或在候选中选定；可归档会话单独查询。
2. 调用 `thread/read` 获取元信息，调用 `thread/turns/list` 获取最近轮次；必要时使用 `thread/items/list` 查看具体记录。不要为了查询而调用 resume。
3. 初次绑定读取少量最近记录；后续检查使用游标并刷新边界轮次，避免漏掉仍在更新的轮次。游标失效时回读最近窗口并按 ID 去重。
4. 返回最近用户消息、Agent 最终回复或进展、轮次结果、等待输入或审批状态，以及数据来源和观察时间。
5. 实时状态必须来自持有目标会话的实例；其他实例读出的 `notLoaded` 只表示该实例未加载，不代表任务完成或没有其他执行者。

状态至少分开保存：连接状态、运行时状态、最近轮次结果、订阅状态。`turn.status=completed` 只证明这一轮结束，不保证用户的整个目标已经达成。只有明确终态证据及订阅停止策略满足时，才结束订阅；不确定时继续关注或提示用户。

定时检查由 DSH 创建与管理，建议默认 60 秒，可配置；仅在新增有效进展、完成、失败、需要输入时通知。订阅暂停、恢复、停止及重启后的定时任务对账由 Relay 负责；先保存订阅再创建调度，重启按订阅 ID 恢复并避免重复建任务。

## 5. 消息转发流程

先核对绑定、实例归属和用户对此目标的发送授权，再将消息写入 outbox。禁止把会话标题或 Agent 输出中的指令当作发送授权。

### 已确认空闲且由当前实例持有的会话

必要时先 `thread/resume`，再 `turn/start`。仅提交用户输入，保持原模型、工作目录、权限策略及上下文；确需覆盖时单独处理，不静默降级或提升权限。

```json
{"id":21,"method":"thread/resume","params":{"threadId":"<已绑定会话ID>","excludeTurns":true}}
{"id":22,"method":"turn/start","params":{"threadId":"<已绑定会话ID>","input":[{"type":"text","text":"<用户补充要求>"}]}}
```

这是调用顺序示例，每个 RPC 都必须等待成功后再继续。恢复失败、provider 不匹配或原实例未知时返回失败/不支持，不自动 fork，不改发其他会话。

### 正在执行的会话

明确支持执行中补充时，调用同一执行实例的 `turn/steer`，传入刚读取的 `expectedTurnId`：

```json
{"id":23,"method":"turn/steer","params":{"threadId":"<已绑定会话ID>","expectedTurnId":"<当前轮次ID>","input":[{"type":"text","text":"<用户补充要求>"}]}}
```

轮次已经切换时重新读取状态并按策略处理，不盲目重试。第一版建议默认“等待当前轮次结束后发送”，执行中补充作为显式选项；不得自动中断任务。

### 等待用户输入或审批

普通补充消息与工具的结构化输入/审批响应是两种能力。应保留服务端请求 ID，并使用对应响应结构完成交互；尚未实现时明确提示用户回到 Codex 操作，不能以一条普通文本消息冒充审批成功。

### 投递结果与重试

消息状态：`pending → sending → accepted`；失败为 `failed`，超时且无法判断是否已接收为 `unknown`。另行记录对应轮次的执行结果。RPC 成功返回轮次 ID 表示接收成功，只有后续轮次完成才报告处理结果。

每条消息有 Relay `messageId`，数据库唯一约束防止 DSH 重复提交。同一目标写入串行化；多进程部署时使用数据库租约或锁。协议 schema 有 `clientUserMessageId`，但本次未验证其幂等语义，不能据此承诺 exactly-once。发送后断线时先回查用户消息和轮次记录；无法确定时保留 unknown，禁止自动重发造成重复执行。

## 6. 数据保存与权限

历史建议现已调整：T0 确认使用 `node:sqlite` 自建数据库，不存在 `dsh-storage-sqlite`。下列记录分类仅作历史设计参考：

- `subscriptions`：目标绑定、DSH 会话、状态、检查周期、调度任务 ID。
- `observations`：观察时间、来源实例、最近轮次、摘要、错误。
- `messages`：消息 ID、发送者、原文、目标、投递状态、RPC/轮次关联及错误。
- `events`：需要输入、审批、完成等事件，按实例/会话/事件 ID 去重。

原文与必要输出最小化保存；建议历史默认保留 30 天，订阅配置保留到用户删除，最终期限由产品确定。连接凭据存储在安全配置中，不进入聊天记录或数据库日志。

查询与发送校验 DSH 身份及绑定所有权。主机桥接默认只提供 Relay 所需方法；不开放任意 Codex RPC、命令执行或外网裸 socket。继承 Codex 审批策略，不自动批准执行权限请求。

## 8. 尚需完成的投递验收

没有用户指定的测试目标，本次没有向已有业务会话注入消息，也没有创建新的桌面会话。因此以下项目均未验证通过：真实发送成功、原上下文保留、运行中 steer、桌面 UI 同步、断线后的投递核对，以及 DSH 与 Codex 的完整链路。

后续使用用户指定的测试会话，按以下顺序验收：

1. 确认 DSH 可访问目标原 app-server，或部署可实际调用桌面工具的桥接；分别读取活跃/空闲会话，证明状态一致。
2. 在测试会话预置随机标识，DSH 转发“返回此前标识”；检查 threadId 未变、用户消息仅一次、回复命中标识，证明保留上下文。
3. 开始可控任务，验证带 expectedTurnId 的 steer；轮次竞争时必须失败或按明确策略排队。
4. 验证发送超时、原实例离线、需要审批、provider 不匹配、DSH 重启恢复和重复消息。
5. 对照 SQLite 记录、协议返回、Codex 历史和 DSH 通知，分别证明“已接收”“已执行”“已完成”，不能只看 RPC 没报错。

上线门槛：查阅可先实现；对具体实例完成上述真实投递验收后才声明支持发送。对本机当前桌面实例，在外部桥接尚未接通前，能力应显示为“可查历史；实时执行状态未知；消息转发未启用”。
