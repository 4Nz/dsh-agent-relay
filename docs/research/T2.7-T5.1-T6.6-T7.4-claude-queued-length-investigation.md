# T2.7 / T5.1 / T6.6 / T7.4 Claude 消息 queued 与正文长度排查

记录日期：2026-11-18；时间使用 Asia/Shanghai。

## 结论及证据边界

- `held=true` 表示会话被进程持有，不表示挂起。channel 投递不检查 held，而是检查会话 idle、在线登记、等待中的长轮询，以及是否存在未 ack 的前条消息。
- 正文旧上限 500 来自 `src/services/relay.ts` 的通用字符串校验和前端 `maxLength`，并非 Claude channel 的硬限制。
- Claude Code 2.1.311 的真实专用会话已完整收到 500、2000、4000 码元消息，三条均回报正确末尾标记并成功 ack。逐条将 Relay 保存的完整正文与 Claude `origin.kind=channel` 的记录比对，均完整包含，没有截断。只能据此确认所测长度可用，不宣称协议无限长。
- 已稳定复现：MCP server 连接、长轮询正常，不等于 Claude 已启用 channel。不带 channel 参数恢复会话时，Relay 仍把首条记为 sent，Claude 明确跳过通知注册，首条没有进入会话、没有 ack，下一条保持 queued。
- 原业务会话的首条未 ack 阻塞已由数据库确认；首条没有进入历史的具体原因缺少事发时的 Claude 启动日志，不能把对照实验结果直接当作该次事故的唯一根因。

## 原业务会话只读核查

仅查询用户指定原业务会话的 Relay 消息元数据、Claude channel 事件/ack 调用和进程信息，未向该会话发送测试消息或修改历史。

| 时间 | 事实 |
| --- | --- |
| 11 月 17 日 11:06:30 | 55 字消息因未有在线 channel 登记被拒绝 |
| 11 月 17 日 11:22:13 | 另一条 55 字消息有 `channel:` 引用，最终因未确认记为 unknown |
| 11 月 18 日 14:05:33 | 48 字消息先记为 sent，acked_at 为空 |
| 14:05:59～14:10:05 | 后续 9 条消息 queued，长度分别为 97、182、121、216、419、177、315、134、99 |
| 14:09:43 | 当前 Claude 进程启动，说明首条发送之后会话又有过一次重启；不能用当前启动状态反推 14:05 时状态 |
| 早期排查 | 原会话进程为 busy，且存在 `lib/channel/main.js` 子进程；当时未找到实际 channel 用户事件或 ack 调用 |
| 14:35 之后 | 48 字首条自动变为 unknown，证明 30 分钟 ack 超时在运行；后续仍 queued，此时 busy 条件亦会阻止推送 |
| 15:11:27～15:12:51 | 历史队列中的 182 字消息已进入原会话的真实 channel 记录，Claude 调用了 ack，Relay 数据库也记录了确认 |
| 15:13:17 | 下一条历史消息转为 sent，后续消息仍排队 |

因此不能归因于“held 挂起，按 Enter 即可”。前条未 ack 是初始队列阻塞的确定原因；超时后仍需重新检查忙闲和 channel 的真实接收能力。事件末次活动时间差也不能当作空闲时长。

后续记录证明原会话恢复了接收能力，历史队列会延迟后来的消息；不能继续把该会话描述为始终无法接收。未人工补 ack、清空队列或重发历史消息。

## shell 加载与真实 DSH 验证

用户确认：退出后新开终端再恢复会话，会显示 `Channels: server:agent-relay`；在安装前打开的旧终端中仅退出再恢复，则未出现该提示。本机 shell 配置中的包装函数与项目生成内容一致，`--resume` 不在管理命令透传列表中，会正确追加 channel 参数。安装写入配置文件不会更新已经运行的父 shell，必须新开终端或显式 `source` 后再启动 Claude。

按用户指定，另向新窗口中的会话通过真实 DSH `relay_send` 发送一条 210 字符测试消息：15:10:27 创建，15:10:28 sent，15:10:44 ack，用户亲眼确认收到。这验证了该窗口的 DSH → channel → Claude → ack 链路；没有创建关注或定时任务，也不代替完整 T7 验收。

## 实验环境与方法

- 仓库基线：`135404a`，插件版本 0.1.9；Node.js 24.14.0；Claude Code 2.1.311，使用本机配置的模型与认证。
- 专用测试会话：`3dbb6195-66f6-470b-abd5-7409c50e5829`。
- 在临时目录启动隔离 Relay HTTP 服务，使用项目真实 `createClaudeChannelService`、`createChannelRoutes`、SQLite 存储、`createClaudeAgentList` 与 channel server；不启动第二个生产 DSH。
- Claude 使用真实伪终端、`--strict-mcp-config` 指向单独测试 MCP 配置，禁用 hooks 和内置工具，只允许测试 ack。测试专用凭证保存在临时文件，不写入本文或仓库。
- 长度实验直接向隔离 Relay 的 channel 队列放入消息，刻意绕过原 500 校验，目的是区分插件业务限制与实际 channel 能力。这不是生产 DSH `relay_send` 的全链路验收。
- 正文带唯一 UUID、BEGIN/END 标记，中间填充汉字；长度按 JavaScript `string.length` 计算。Claude 将末尾 END 标记写入 ack 摘要，另只读核对完整正文已进入会话历史。

## 不带 channel 参数的对照实验

1. 正常退出测试 Claude；使用同一 ID、同一目录与 MCP 配置恢复，唯一关键改变是去掉 `--dangerously-load-development-channels server:agent-relay`。
2. Claude 日志显示 MCP 成功连接，随后明确记录：

   ```text
   Channel notifications skipped: server agent-relay not in --channels list for this session
   ```

3. 发送 500 码元消息 `f8d041e7-cc77-4f56-a013-b55af4e1e749`：Relay 为 sent、无 ack；完整正文未进入 Claude channel 历史。
4. 再发送 501 码元消息 `9a633b48-fe1b-4c25-9472-c43f066cfe0d`：保持 queued。测试会话 idle，仍被首条未确认阻塞。

这不是某个老会话独有的历史损坏：一个刚刚成功收取三条消息的会话，改变启动方式后也出现同样症状。生产 shell 包装函数只对经过该函数的启动生效；直接运行二进制、其他启动器或未加载配置的 shell 不能凭 MCP 登记就推断 channel 已启用。

恢复对照：再次正常退出测试 Claude，仍恢复相同 ID 和会话历史，补回 channel 参数。使用新的隔离 Relay 数据库排除上一轮未 ack 队头的影响，原实验库保留不改。14:42:05 发送新的 2000 码元消息，14:42:08 收到正确 END 标记 ack，完整正文比对通过。没有人工补写 ack，也没有修改 Claude 历史；此步骤验证恢复后的新消息可送达，不宣称旧 unknown 消息会自动补发。

原始实验材料保存在本机临时目录，未加入仓库；不上传测试凭证文件或原始完整调试日志。实验 Claude 进程与临时 Relay 服务已退出。

## 本次已实施的修改

- 正文独立校验为最多 2000 UTF-16 码元；普通汉字通常计 1，部分 emoji 计 2。不改变会话 ID 等其他字段的校验。
- 空内容与超长内容分开报错。超长提示发送方先汇总，或将完整内容存成接收方可访问的文档，发送摘要与路径，不自动拆分。
- 前端输入框同步 2000 上限与文档发送建议。
- `relay_send` / `relay_inspect` 工具说明纠正 held 和 channel sent 的含义，说明前条 ack 对后续队列的影响。
- 新增正文边界回归：2000 汉字完整落库并交给 Adapter；2001 汉字和 1001 个双码元 emoji 被拒绝，不新增消息；空白及非字符串仍拒绝。
- 自检和重复安装均提示旧终端需重新加载配置，区分“函数已写入文件”和“当前 shell 已加载”；恢复会话的指引明确先加载配置再执行 `--resume`。
- 用临时假 Claude 命令在真实 bash / zsh 中核验 argv：加载前不追加，加载后交互、`--resume`、`--continue` 正确追加，含空格参数完整保留，管理命令及 `-p` 透传。未改变现有包装函数内容。

## channel 修复建议（尚未实施）

本轮按用户要求暂不实施队列清理、接收就绪验证或 ack 协议改造；以下是后续建议，不属于本次已交付能力。

1. 将“传输在线”和“本次 Claude 进程已验证可接收 channel”分开。现有 poll 仅能证明 MCP 子进程在线；不能把它当作启用成功。若官方提供就绪信号，应优先使用；否则用专用探测消息与 ack 证明可接收，验证状态应绑定当前进程实例/会话，重启后失效。不能仅增加一个可随便声明的 enabled 布尔值当作证明。
2. 在 `relay_inspect`、发送结果和页面暴露实际等待原因：busy、无长轮询、channel 接收未验证、等待前条 ack（含阻塞消息 ID 和截止时间）、状态查询失败。unknown 只代表结果未知，不能提示用户直接重发。
3. 区分 Relay 已交付轮询、Claude 已收到、Claude 已处理。现有 sent 在 HTTP 轮询返回之前写入，不能等同于 Claude 接收确认；MCP 写出成功也不等同于模型看见。
4. 保持同会话顺序及 unknown 不盲重发原则；不要用“忽略 held”“强制 --resume 注入业务进程”“缩短超时后不断重发”掩盖接收能力缺失。是否将接收确认和处理结果拆成两个事件，需单独确定协议与迁移方案。
5. T7.4 后续应覆盖：缺少 channel 参数、首次注册/重连窗口、恢复已有会话、忙转闲、多条消息前条不 ack、真实 DSH 启动与重启。本次隔离实验不替代完整 T7。
