# T3-T7 通知发送沙箱权限诊断修复

记录日期：2026-11-19。涉及 Codex 会话 `01a1e8ad-6154-76d0-bbc5-3195fce2ae41`（评估 WorkBuddy 会话读写方案）。

## 证据与原因

原会话两次调用已安装的 `dsh-notify/send.mjs`，复用事件 ID `workbuddy-acp-review-20261119`；均只得到“通知连接失败或结果未知；确认 DSH 已启动”。随后受限环境内的 GET 也失败，因此报告本机 DSH 无法连接。原调用记录没有保留底层异常码，不能由此证明当时服务停机。

本轮只读对照检查：

- 配置指向 `127.0.0.1:37421/api/agent-relay/notifications`，通知端口存在监听进程。
- 沙箱内 Node `fetch` 的 `cause.code` 为 `EPERM`。
- 经执行工具权限审批后，对同一地址发送无凭证、无正文的 GET，返回 HTTP 405，确认通知接口可达。
- 只读查询 Relay 事件表，未找到 `push:workbuddy-acp-review-20261119`。本轮未重发该业务通知，未写生产事件或修改凭证。

据此确认当前执行环境会阻止本机回环连接，原脚本的统一错误提示掩盖了权限问题。该问题发生在通知入口连接之前，与 Claude channel、held 状态或接收会话的归档状态无关；接收后的投递问题仍需独立判断。

## 修复

发送脚本仅读取白名单错误码，分别提示 `EPERM/EACCES`、`ECONNREFUSED`、超时及其他结果未知，不打印原始异常、请求头或凭证，也不自动重发。权限错误明确要求通过执行工具正常审批，获准后保留原会话 ID、事件 ID 和摘要重试。

Skill 增加回环网络也受沙箱限制的说明，禁止在同一受限环境中盲目重试；说明 GET 返回 405 只证明接口可达，只有 POST 返回 202 且 `accepted: true` 才能确认接收。

已将两个修复文件同步到本机 Codex 的 `~/.codex/skills/dsh-notify/`，更新前核对其与仓库原版哈希相同，备份位于 `~/.codex/skill-backups/dsh-notify/20261119T104756/`。未改其他 worktree、Claude 已安装 Skill 或运行中的 DSH 插件。后续安装包升级应包含本次 Skill 修复，防止旧包重新安装时覆盖。

## 验证

新增五类传输异常回归，验证错误分类、保留原事件 ID 提示、不泄露凭证及单次调用不自动重发。`rtk npm run release:prepare` 通过类型检查、313 项单测、干净构建、包清单检查和隔离 tarball 安装冒烟。

以上验证不代表原业务通知已接收。原会话后续重试仍须通过其执行工具的网络权限审批；脚本不会自行提升权限或绕过审批。
