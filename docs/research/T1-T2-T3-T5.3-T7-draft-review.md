## 合并前阻塞项

1. **通知状态与路由**：当前候选修复将 delivered 自动转 processed，丢失 DSH 处理确认语义。idle=false 和查询失败也会触发新建接收会话，混淆忙碌、不可达与归档；重复 request_id 可能在幂等判断前产生重绑副作用。必须保留原路由排队、原批次确认和未知不重发规则，使用明确的归档证据设计恢复策略。
2. **修正此前诊断**：没有 `relay_notification` 不代表桥梁没有投递链路；新桥梁使用 `relay_bridge_batch`。本次实际观察是旧规划批次停在 delivered、未确认处理，新 push 尚未绑定批次；接收会话另有归档记录。二者需要分别处理。不能依靠自动 acknowledge 掩盖未处理事件。
3. **旧数据库升级**：当前 WorkBuddy 约束改在历史迁移里，已有数据库不能因此获得新能力。需要追加迁移并验证旧数据保留、外键、幂等键及失败回滚，不能直接部署当前草稿。
4. **只读状态**：非 live 会话被标 idle，以及历史缺失时间时合成当前时间，可能导致错误空闲或新活动判断；需要改为事实来源明确的未知状态与稳定游标。
5. **通知 Skill 接入**：WorkBuddy 安装指引可能被通用 finish 覆盖，随包发送器尚未完成 WorkBuddy 来源支持与真实回传验收。
6. **ACP 与宿主验收**：需证明目标项目端点、对话与 worker 绑定，再验收 A/B 精确投递；当前真实请求返回 -32603，不能用合成测试替代成功投递。完整 T7 与 Windows 验收仍未完成。

详细 ACP 证据见 [T5.3 ACP 验证记录](T5.3-workbuddy-acp-validation.md)。修复上述阻塞项后，需重新检查测试契约、执行交付检查，再将草稿转为可合并状态。
