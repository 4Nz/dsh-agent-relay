# T1-T3-T6-T7 接收会话未读提醒修复

日期：2026-11-20。接口核对版本：DSH 0.2.1-rc.2。插件版本：0.1.9 未发布改动。

## 问题与证据边界

外部通知投递到已有 DSH 会话后，用户在其他会话中未看到侧栏提醒。已核对目标通知落库、接收会话回复及轮次结束；该轮结束之后没有新轮次，不能用“下一轮清除标记”解释这一次现象。

DSH `uiSession.completionUnread` 是前端内存中的后台完成提醒，依赖观察到运行状态转换，不是持久化的消息已读记录。页面刷新会丢失标记，断线期间错过完整轮次也没有投递回执用于补偿。控制台曾出现连接丢失及会话引用失效，但无法追溯到本次推送时点，不能据此断言此次精确触发原因。

## 修复行为

- SQLite v8 新增 `relay_receipt` 与 `relay_read_cursor`。记录原接收会话和稳定投递键，不存消息正文，投递键防重；已读水位单调递增，且只能确认属于目标会话的已有序号。
- `createDshDelivery` 在 `flush` 成功后记录回执；未知投递经原日志核对及 `flush` 确认后也记录。pending、失败和未确认的 unknown 不亮标记。重试核对不会重置已读，路由重绑不会迁移原会话的未读。
- 页面通过 `unread` 获取每个会话最新未读回执，通过 `mark_read` 确认精确水位。旧水位请求不能吞掉后来到达的消息。两个接口不加入模型工具。
- 独立控制器挂在 `shell.overlay`，每 5 秒对账；不依赖侧栏展开、浏览器 Notification 权限或旧 `notify_poll` 游标。失败时保留当前提示，后续轮询恢复。
- 通过公开的 `sessions.list`、`sessions.binding().session/eventSource` 与 `layout.panelInfo` 判断阅读：主会话确为接收目标、会话加载成功且空闲、事件窗口含该投递键及之后的轮次结束、没有全局面板遮挡、页面可见且有焦点。这里只表示用户打开了已加载回复，不声称能判断是否读完每个字。
- `sidebar.session.row.leading` 显示蓝点，提示“外部消息未读”；hover 卡显示说明。宿主运行、待审批或完成标记会优先占用前导单元格，插件记录仍保留，恢复空闲后仍可显示。归档行遵循宿主不显示前导标记的约定。
- 升级前的已送达历史不批量补红点。回执与已读游标独立保存，不随订阅历史清理而丢失防重信息；当前仅保存小型标识记录，未引入自动过期。

## 验证

先新增失败回归，再实现持久化、投递接入、RPC 和前端控制器。测试使用临时 SQLite 与隔离宿主接口，不访问业务会话。

- 投递未知后确认、重复核对防重、已读后再次投递、重开数据库。
- 旧库 v7 升级保留既有批次，不把历史批次标为未读。
- 同时到达的新消息、不同接收会话、越界或非整数水位、旧请求不回退游标。
- 断线、重新挂载、页面隐藏、全局面板、加载失败、消息未加载和轮次未结束不误清除。
- 已读请求在途收到新消息、RPC 失败恢复、控制器卸载清理，以及实际客户端 bundle 的插槽注册与标记渲染。
- `rtk npm run release:prepare` 通过：类型检查、320 项单测、干净构建、包清单及隔离 tarball 安装冒烟。首次沙箱运行因临时端口监听 EPERM 及相关 Node 异常中止，授权环境重跑全部通过。

## 尚未完成的真实宿主验收

尚未替换用户当前运行插件，未发送真实 Agent 消息，不将隔离测试或安装包冒烟等同于 T7 验收。安装新包并重新加载插件后，在专用测试会话验证：

1. 选中其他会话，向接收会话发送通知，确认后台结束后有状态提示。
2. 不打开接收会话，刷新页面，再确认插件蓝点恢复。
3. 打开任务跟踪面板、切到其他浏览器页，不应消除记录。
4. 打开接收会话，等待回复加载并结束，确认插件标记消除；再次推送应重新出现。
5. 页面断线期间完成第二次推送，重连后确认补回未读；原有业务队列无需清空或重发。
