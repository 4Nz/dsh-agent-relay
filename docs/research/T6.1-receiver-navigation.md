# T6.1 跟踪列表接收会话跳转修复

记录日期：2026-11-19。

## 现象与已确认原因

用户反馈跟踪列表点击“打开会话”后进入新会话页面。本机 DSH 0.2.1-rc.2 的浏览器验证中，未归档的“mem解答”能够打开既有接收会话并显示历史 18 轮对话；已归档的“评估 WorkBuddy 会话读写方案”则回到“探索未至之境”的空白首页。

插件原来直接调用 `uiWorkspace.openSession(subscription.dsh_session_id)`。宿主的 `replaceMain` 打开指定会话后，`clearArchivedCurrent` 会清空已归档会话的选择，造成看起来打开新会话的现象。这条导航路径本身没有创建新会话。用户原窗口“所有记录都如此”的现象尚未完整复现，不能将其全部归因于归档。

## 修复行为

- 列表和详情按钮统一命名为“打开 DSH 接收会话”，明确目标是 DSH 接收端；详情移除重复入口。
- 新增只读 `dsh_session_status` 接口，按指定 ID 查询当前存在性及归档状态，不读取会话正文。
- 未归档且存在时打开原接收会话；已归档时提示用户先恢复；不存在时明确提示；查询失败时保留错误并留在原页面。
- 历史订阅仍使用该订阅持久化的接收 ID，不以当前桥梁路由替换，不新建或自动恢复会话。
- 跟踪面板内的“继续原关注”和路由入口共用同一导航检查。

## 验证范围与限制

回归测试覆盖宿主状态分类、恢复后的状态更新、查询失败、接口参数校验、列表阻止异常跳转及历史目标保留。既有详情测试验证详情正常渲染，共用按钮行为另以回归测试验证。

`rtk npm run release:prepare` 已通过：类型检查、308 项单元测试、干净构建、包清单检查与隔离 tarball 安装冒烟；`rtk git diff --check` 通过。

本次不改变浏览器系统通知点击入口。打开前查询与宿主实际打开之间不具备事务性，极短时间内被另一个窗口归档的竞态仍由宿主处理。本地测试与打包验证不等同于已安装到运行中的 DSH；本次未自动升级或重启用户宿主。
