# T2-T3-T7 主动通知阻塞与归档接收会话恢复

验证日期：2026-11-19。基线：`main` 的 `11ebbb0`；插件版本 `0.1.9`，Node.js `v24.14.0`，macOS。此修复覆盖 Claude/Codex 共用通知桥梁，不包含 WorkBuddy Adapter、协议或发送接入。

## 问题与处理原则

旧关注已结束，但其批次仍为 `delivered`（宿主接收、模型尚未确认处理），会占用该来源的开放批次；后续通知虽已落库，却无法形成新批次。若原 DSH 接收会话已归档，即使释放旧批次，原目标也不能被唤醒。

HTTP `accepted` 只表示接收成功，`delivered` 只表示投递成功，只有 `relay_decide` 才确认批次处理完成。桥梁通知使用 `relay_bridge_event` / `relay_bridge_batch`，不能因旧 `relay_notification` 无记录就推断没有投递路径。

## 修复行为

1. `drain` 发现无 active/paused 关注、路由未屏蔽，且存在未绑定批次的新 push 时，将阻塞的旧 `delivered` 批次转为 `needs_attention`。旧事件的 `processed_at` 保持空，保留原目标与事实，不重放、不自动确认；旧恢复提醒删除失败由后续对账清理。
2. `unknown` 仍首先向原目标核对。无法确定时保留未知且不创建新目标；明确已送达后才允许转待人工。明确未送达沿用原批次重试规则。已有 `pending` / `exhausted` 等批次保持原接收目标。
3. 无开放批次且仍有上述新 push 时，通过宿主 `workspaceRegistry.archivedSessionIds` 判断原目标是否明确归档。只有明确归档才创建新接收会话并更新路由。`idle=false`、加载失败、查询异常均不等价于归档。
4. 新目标繁忙时继续等待，后续 push 复用同一目标。新消息保持 `delivered` 直到模型调用 `relay_decide`；不会自动恢复已结束关注。重复 `request_id` 保持事件和投递幂等。
5. 创建替代会话后再次检查路由、关注、屏蔽与归档状态，避免覆盖期间发生的用户选择。push 响应返回当前实际路由目标。创建失败保留原路由与事件，后续维护重试。
6. 该逻辑在共用维护 drain 中执行，符合条件的既有积压事件可以恢复，无需修改业务数据库或重发原请求。仅收到 push 不读取外部会话历史。

## 隔离验收

所有测试使用临时 SQLite 和模拟宿主；不读取真实会话内容、不包含凭证。

| 能力与场景 | 结果及边界 |
| --- | --- |
| 结束关注后旧 delivered 规划阻塞新 push | 已验证转 needs_attention；旧事件仍未处理，新批次可投递并由 decide 确认 |
| 无关注的旧 push 未确认，新 push 到达 | 已验证新批次可投递；旧批次迟到确认只处理自身事件 |
| 原接收会话明确归档 | 已验证新通知创建一个新目标；响应返回新目标，同 request_id 不重复投递 |
| 已落库积压事件，无新的 HTTP 请求 | 已验证维护 drain 恢复；旧批次保留原目标，新目标只接收新事件 |
| 原会话 busy、查询异常、归档查询异常 | 已验证不重绑、不投递，事件保留 |
| 新目标 busy、创建目标失败 | 已验证繁忙时复用目标；失败保留事件，下轮可重试 |
| active/paused 关注或屏蔽 push | 已验证不自动迁移接收会话 |
| unknown 未知投递 | 已验证保留原目标核对，不重发、不新建；确认已送达后可释放旧批次 |
| pending 批次已绑定原目标 | 已验证即使原目标归档也不自动迁移旧批次 |
| 创建期间重绑、解除归档、屏蔽、重新关注 | 已验证不覆盖用户新选择、不向创建出的替代会话投递 |
| 旧恢复提醒清理暂时失败 | 已验证新通知继续投递，后续 reconcile 清理旧提醒 |
| 真实宿主投递、DSH 模型汇报和 decide | 尚未验证；本次不部署，也不修改真实数据库 |

## 真实宿主补测与限制

合并并安装后，使用专用 Claude/Codex 来源和专用 DSH 接收会话：建立并结束关注，保留一个已投递但未确认的批次，归档原目标，再发送唯一 request_id 的测试通知。核验新目标仅收到新通知、模型向用户汇报并调用 decide、旧批次仍待人工且事件未被伪造处理；同 request_id 重试不再投递。另对忙碌、活跃关注、屏蔽和 unknown 场景验证不误迁移。

旧待人工批次不会自动被新会话处理；需要人工核对原会话。已绑定 pending 批次仍留在原目标，需恢复原会话或人工处理。若宿主不提供明确归档信息，继续保留原路由等待。若创建替代会话期间发生并发选择，可能留下未使用的新会话；本修复优先不覆盖用户选择，不自动删除宿主会话。宿主创建会话成功但返回失败或进程中断的跨系统幂等不在本次保证范围内。
