# T5.2/T7.4 Codex 桌面占用会话发送可行性调研

状态：**已实测打通 —— `thread/queue/add` 是「桌面占用时发送」的正解**。

调研日期：2026-11-13（Asia/Shanghai）。环境：Codex CLI 0.163.0、daemon（app-server）0.168.0、Codex Desktop（ChatGPT.app 内嵌 Codex CLI）。

## 结论（一句话）

**`thread/queue/add` 能绕过桌面 `active writer` 独占，向桌面占用中的会话排队投递消息，agent 自动醒来处理。** 实测：对桌面占用会话 `01a1d43f`「测试消息流程」发 `queue/add` → 消息入队 → 桌面 agent 醒来回复「能看到，已收到这条标注为通过 queue/add 排队的 DSH 测试消息。」（无需 `queue/start`，agent 自动消费）。

- 参数格式：`{ threadId, input: [{ type: "text", text }], clientUserMessageId: <uuid> }`。
- 返回：`{ queuedSubmission: { id, input, clientUserMessageId } }`；随后 `thread/queue/list` 可见该排队项。
- 对比：`turn/start`/`thread/resume` 被 `active writer` 拒；`turn/steer` 需 `expectedTurnId`（拿不到）；`thread/queue/add` 是唯一绕过的正解。

## 实现方案

1. `src/adapters/codex/rpc.ts`：`WRITE_METHODS` 增加 `thread/queue/add`（当前仅 `thread/start`/`thread/resume`/`turn/start`）。
2. `src/adapters/codex/index.ts`：`sendMessage` 对**桌面会话**改用 `thread/queue/add`（排队投递）；专用会话保持 `turn/start`。
3. `info()`：桌面会话 `send_allowed` 放开（不再只读）。

（附：曾尝试的 `agent_message_board`/`multi_agent_v2` feature 路线是弯路，`queue/add` 是 daemon 原生方法，不依赖 feature。）

## 背景与问题

当前 Codex 边界：桌面会话只读，仅 Relay 通过 `thread/start` 创建并登记到 `relay_codex_session` 的**专用后台会话**可发送（`turn/start`）。父皇要求：**桌面端占用会话时也能发送**。

## 已确认的 daemon 机制（从 daemon 二进制 0.167.2 提取）

daemon 提供完整 RPC 方法集，其中与「向占用会话发送」直接相关：

| 方法 | 语义 |
| --- | --- |
| `turn/start` | 开始新 turn（空闲时投递） |
| `turn/steer` | 向 **active turn** 注入指导（忙时 steer）；`no active turn to steer`、`cannot steer review/compact turn`、错误码 `active_turn_not_steerable` |
| `turn/interrupt` | 中断当前 turn |
| `thread/queue/list` `update` `delete` `reorder` `start` | 排队提交（`queued_items`/`queuedSubmission`）：忙时把输入排队，空闲时投递 |
| `thread/inject_items` | 注入 items |
| `thread/resume` | 把 `notLoaded` 会话加载回 daemon |

语义证据（daemon 内嵌字符串）：
- `send_input` 工具说明：「If the background agent is idle, this starts a new task… If the background agent is already working on a task, this sends the request as guidance to **steer** that previous task.」—— 明确「闲时 start、忙时 steer」模式。
- `[desktop] migratedFollowUpQueueToSteer = true`（config.toml）—— 桌面端已把「follow-up queue」迁移到「steer」，即桌面「忙时输入」走 steer。

**结论**：Codex 原生就有「忙时 steer / 排队、闲时 start」的机制，与 Claude channel 方案（AGENTS.md 已定）一一对应。

## 实测：daemon 对会话的感知

`thread/read`（`includeTurns:false`）实测：

| 会话 | source | originator | status | canAcceptDirectInput |
| --- | --- | --- | --- | --- |
| `01a1cf19`「测试消息」（桌面） | `vscode` | `Codex Desktop` | `notLoaded` | `null` |
| `01a1d373`「审阅文档治理方案」（桌面） | `vscode` | `Codex Desktop` | `notLoaded` | `null` |
| `01a1d2cf`（Relay 专用会话） | `vscode` | `dsh-agent-relay` | `notLoaded` | `null` |

关键点：
1. 桌面会话与 Relay 专用会话 **daemon 都返回 `notLoaded`**（未加载）；区别只在 `originator`（`Codex Desktop` vs `dsh-agent-relay`）。
2. Relay 专用会话可发送的路径是：`notLoaded` → `thread/resume`（加载）→ `turn/start`。
3. `canAcceptDirectInput` 两者都是 `null`，非发送判断字段。

## 核心风险点（已实测：B 成立，桌面占用时 daemon 不可介入）

对桌面会话 `01a1cec4`（「确认 Codex 会话消息发送能力」，originator=Codex Desktop）直接调 daemon 协议实测：

| 方法 | 结果 |
| --- | --- |
| `thread/resume` | ❌ `thread ... already has an active writer`（桌面独占写锁） |
| `turn/start` | ❌ `thread not found`（notLoaded 且被占用，daemon 不认） |
| `thread/inject_items` | ❌ `thread not found` |
| `turn/steer` | ❌ 需 `expectedTurnId`，但 daemon 拿不到桌面 active turn |
| `thread/queue/list` | 空（daemon 不管理桌面会话队列） |

**结论：桌面会话被 Codex Desktop 独占（`active writer`），daemon 是外部执行后端，两者是写锁竞争关系，resume/start/inject/steer 全部无法介入。** 这与 Claude 的「held 冲突」同构；`active writer` 就是 Codex 版的「会话被进程持有」。

## 候选机制（remoteControl 实现方式与局限）

### remoteControl 怎么实现

- **启用**：app-server daemon 启动时加 `--remote-control --listen ws://IP:PORT`（或 `unix://PATH`），暴露远程控制端点；CLI 有 `codex remote-control` 子命令管理。
- **认证/配对**：端点带 TLS（CA 证书）+ auth；远程客户端用 `--remote <ADDR> --remote-auth-token-env <ENV>` 连接，走 `remoteControl/pairing/start` 配对（`remoteControl/enable|disable|status/read|pairing/start|pairing/status|client/list|client/revoke`），用户在桌面端确认。
- **远程操作**：配对后，远程客户端（另一个 Codex TUI/CLI）像本地一样操作 daemon 管理的会话（`turn/start` 等）。

### 为什么 remoteControl 不能解决「桌面占用时发送」

remoteControl 只解决「怎么连上 daemon」（配对 + auth + 端点），连上后仍走 `turn/start` 操作会话。而桌面占用会话（`active writer`）的 `turn/start` 已被实测拒绝（`already has an active writer` / `thread not found`）。remoteControl 是「远程控制整个 app-server」，不是「绕过桌面占用向单个会话注入」；典型场景是「跨设备控制一台无人的 Codex 机器」，不是「本机 DSH 给正被桌面占用的会话发消息」。是否可通过配对后「接管」让桌面释放 writer 未验证，但要求桌面端配合，违背「占用时发送」初衷。

## 重大发现：Agent Message Board（桌面占用时发送的官方机制）

daemon 二进制暴露一套 **`agent_message_board`（Agent 消息板）** 机制，正是「向被占用的 Codex 会话发消息」的官方入口，等价于 Claude channel：

- 结构：`board`（消息板）→ `channel`（频道）→ `post`（帖子），SQLite 存储 `agent_message_board_1.sqlite`。
- 工具：`channel.post`、`channel.reply`、`create_channel`、`subscriptions`（订阅）、`manage_permissions`。
- 投递：`<agent_message_board_notification>` 通知 + `wake_on_agent_messages`（agent 收到消息板消息时醒来处理）—— 即使会话被桌面端占用。
- 接口：`agent_message_board_mcp`（MCP）、`agent-message-board-host/client`（host/client 架构）。
- 远程模式：`message_board_remote` + `RemoteMessageBoardConfigToml`（`credential`、`delivery_mode`、`clock_source`、`reminder_interval_seconds`）—— 跨进程/跨机器投递，需要 credential。
- 启用：experimental feature，config.toml 配置如下（字段从 `MultiAgentV2ConfigToml` 21 字段 + `RemoteMessageBoardConfigToml` 3 字段提取）：

```toml
[features]
multi_agent_v2 = true              # 多 agent v2
wake_on_agent_messages = true      # agent 收到消息板消息时醒来处理
agent_message_board = true         # Agent 消息板
agent_message_board_mcp = true     # 消息板 MCP 接口

[features.multi_agent_v2]
message_board_remote = true        # 远程消息板（跨进程/跨机器）；或 message_board_in_memory = true
disable_direct_message = false     # 允许直接消息
# 远程模式凭证：credential_broker / credentials / RemoteMessageBoardConfigToml{reminder_interval_seconds, clock_source, delivery_mode}
```

关键：`message_board_remote`（跨进程投递，需 credential）让 DSH 作为独立进程连消息板发消息；`wake_on_agent_messages` 让桌面 agent 即使被占用也醒来处理。

**结论（修正）**：Codex 桌面占用会话时**可以发送**，路径是「DSH 作为消息板 client → 往 agent 订阅的 board 发 `channel.post` → 桌面 agent 经 `wake_on_agent_messages` 醒来处理」。这是 experimental（`multi_agent_v2`），需要启用 feature + 远程模式配 credential，且 DSH 侧要新增「消息板 client」实现。

## 最终结论（定稿）

**Codex 桌面占用会话时可以发送，机制是 `agent_message_board`（Agent 消息板）+ 多 agent 消息工具 + `wake_on_agent_messages`。**

从 daemon 二进制提取的关键证据：

1. **多 agent 动态工具**：`spawnAgent / sendInput / resumeAgent / closeAgents / sendMessage / followupTask / interruptAgent / listAgents`。其中 `sendMessage`（给 running agent 传消息、不触发 turn）、`sendInput`（给 agent 发输入）正是「桌面占用时发消息」的能力。
2. **消息载荷**：`ThreadItemPayload::AgentMessage{agentThreadId, agentPaths, senderThreadId, receiverThreadIds, agentsStates, …}` —— 跨 agent 消息，可按 `receiverThreadIds` 精确路由到桌面会话。
3. **消息板**：`agent_message_board`（board/channel/post + `channel.post`/`channel.reply` + 订阅），`message_board_in_memory`（本机 `message-board/src/local/connection.rs`）或 `message_board_remote`（远程，`RemoteMessageBoardConfigToml{bearer_token, bearer_token_env_var, …}` 凭证）。
4. **醒来处理**：`wake_on_agent_messages`（feature）—— agent 收到消息板消息时醒来，即使会话被桌面占用。

**落地路径（与 Claude channel 对应）**：
1. 桌面 Codex 启用 `[features] multi_agent_v2 + agent_message_board + agent_message_board_mcp + wake_on_agent_messages`，消息板配 `message_board_remote`（bearer token）；
2. DSH 侧新增「消息板 client」，用 bearer token 连消息板，发 `AgentMessage`（`receiverThreadIds` = 桌面会话）；
3. 桌面 agent 经 `wake_on_agent_messages` 醒来处理。

**风险**：整套是 experimental（`multi_agent_v2`），字段名/协议可能随 Codex 版本变；远程消息板凭证机制需实测确认；桌面端需改 config 并重启。

**待父皇配合的测试**（最小验证）：桌面端开一个会话 + 启用上述 feature，DSH 侧发一条 `AgentMessage`，观察桌面 agent 是否醒来收到。
